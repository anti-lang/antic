# Both VMs at origin/main

`a932827` went to `anti-linux` and `anti-windows` with `git archive`, as
`docs/vm-setup.md` describes, and built there with the pinned clang, LLVM
tools and sysroots. Linux ran the full suite and both sanitizer suites,
Windows the full suite. Nine commits fixed what failed and took the digits of
a float away from the C library. Both VMs then ran again from a fresh export
of `64d77b6`.

## Linux

- The build stopped at `antic_unit_tests`: `test_f16.c` calls `nextafterf`,
  which glibc keeps in libm. `1368828` links `m` there.
- `std_serialize_null` printed a deserialized `str` with `%s`. An empty one
  has one byte from `malloc`, and the VM's was not 0. `421d8f1` prints it by
  its length.
- Five trace tests printed the module `/proc/self/exe`, which the static musl
  gives the program. `02fd471` takes the first module of `dl_iterate_phdr` for
  the program, whatever its name.
- `trace_stack_dev` named a frame `$x`. That is the mapping symbol of
  AArch64, at the address of the first function of each object, and the ELF
  reader took it. `5ae37f5` passes over every name that starts with `$`.
  `trace_symbols_linux-arm64` now links a dev build too, and failed on the Mac
  before the fix.

## Windows

- The three dev tests of traces linked `std_lang.o` where antic writes
  `std_lang.obj`. `0da05d1` takes the suffix of the host in `run_trace.cmake`.
- Every trace lost its first frame. On ARM64, `RtlCaptureStackBackTrace`
  follows the chain of frame records, and `anti_rt_trace_walk` builds none.
  A C program built by clang lost `f` and `main` the same way, and a walk with
  `RtlVirtualUnwind` over the same program found them. `22c3a1c` walks that
  way.
- No frame had a name. DbgHelp looked for the PDB in the working directory
  only, and gave COFF names such as `_A11stack_trace_inner`. `fdf4e14` puts
  the directory of each module on its search path and demangles those names,
  with the unit test `test_symbols`. The three dev tests pass since.
- `std_backtrace`, `trace_stack` and `trace_stack_g` still fail. See
  questions 1 and 2.

## The text of a float

`program_format_strings`, `std_format`, `dump_ast_format` and the four
`listing_error_format_*` passed on all three hosts at `a932827`. A probe of 72
hard cases printed the same text on each. The digits still came from
`snprintf` and `strtod`, and the C runtime of Windows before Windows 10 2004
rounds a tie the other way. `8bcf66e` finds every digit of the exact value
with integers and rounds a tie to the even digit. `std_float_text` holds the
72 lines with one expected file. `float_digits` refuses a runtime whose
object of `rt/text.c` names printf, scanf or strtod. Two million random cases
gave the text of the Mac's C library. `float_digits` then failed on both VMs,
because CMake names the member of the host's runtime `text.c.o`. `64d77b6`
lists the members.

## clib_classes and clib_tuples

Both pass on the Mac and on Linux. They do not exist on Windows:
`tests/CMakeLists.txt` registers the `clib_*` tests under `NOT WIN32` and
leaves Windows to the CI runners. See question 3.

## Questions

1. A release build on Windows names every frame `anti.rt.main`. antic writes
   Anti functions as static COFF symbols, and lld-link carries only external
   ones into the PDB. The entry on COFF debug information writes no symbol
   record per function, because "the COFF symbol table names the functions".
   It names them in the object and not in the PDB. Shall antic write an
   `S_LPROC32` record per function into `.debug$S`, with `-g` and without? It
   reaches the PDB and not the executable.
2. lld-link makes the file of a CodeView line table absolute against the
   directory of the link, so `trace_stack_g` reads
   `C:\...\build\tests\stack_trace.anti`. The entry asks for the path under
   the search root. `/pdbsourcepath:.` gave `stack_trace.anti` in a link by
   hand on the VM, and keeps the build directory out of a `-g` PDB. Shall
   every Windows link pass it?
3. Shall `run_clib.cmake` learn the MSVC toolchain that the Windows VM has,
   so `clib_classes` and `clib_tuples` run there?
4. The entry on the Windows walk is `[provisional]` now. It names
   `RtlVirtualUnwind` in place of `RtlCaptureStackBackTrace`, with the
   evidence above.
5. `rt/object.c` writes floats for `serialize` with `%.9g` and `%.17g`
   through `snprintf`. Shall it take the digits of `rt/text.c`? That changes
   the text `serialize` writes.
