# anti bind: blocked before the first change

The step was `anti bind` from `docs/tooling-addendum.md`: a binding from
`raylib_api.json` and from a C header, the C types, unions, bitfields,
packed and aligned structs, enums, `link framework` lines, the
`static inline` shim and `anti bind --header`. The test was a binding of
raymath from the pinned raylib source, compared with the ABI probe.

Nothing was built. The only commit is this report.

## What stops it

`docs/tooling-addendum.md` under "Binding generator" and
`docs/site/build-tool/index.md` say that `anti bind --clang <header>`
reads the header through libclang. No document says where libclang comes
from, and no pinned artefact carries it:

- The clang archive of `23.1.1-anti.3` holds `bin/clang` and the
  resource directory. It has no `libclang` library and no `clang-c`
  headers.
- `docs/decisions.md` says the installers never download clang, so a
  user of `anti` has no clang and no libclang on the machine.
- The pinned raylib 6.0 source ships `raylib_api.json` alone, in
  `tools/rlparser/output/`. raymath has no JSON description there, so
  the requested test needs the header path.

Every way around this is a design decision that the documents do not
hold, and the task rules say to stop rather than make one. The options,
without a recommendation, since the choice is the owner's:

1. `anti-lang/llvm-tools` builds and ships `libclang` with its `clang-c`
   headers for the six hosts. `anti` links it or loads it at run time.
   This matches the text of the addendum and changes another repository
   and every package.
2. `anti bind --clang` runs a clang binary with `-Xclang -ast-dump=json`
   and reads the JSON. The parser is clang's own, with no library to
   ship, but a user would need a clang that the installers do not give.
   The addendum would change from "libclang" to this.
3. `anti bind --clang` uses the libclang of the machine, as Xcode's
   Command Line Tools provide on macOS. That breaks the rule that the
   compiler a machine happens to have is never used.
4. The raymath test builds `rlparser` from the pinned source and binds
   the `raymath_api.json` it writes. That covers the JSON path and not
   `--clang`, and the JSON does not say which functions are
   `static inline`, so the shim would rest on the value of `RMAPI`.

## Questions for Eddie

- Where does libclang come from for `anti bind --clang`, on the build
  machine and on a user's machine? One of the options above, or
  another.
- May the JSON path and `anti bind --header` land in a session of their
  own before the header path is settled, or must the step land whole?
