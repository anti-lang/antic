# The sorted collections of round five: `union` and `==` of the map

The session finishes the step that `docs/reports/2026-09-25-add5-sorted.md`
left BLOCKED. `SortedMap<K, V>` and `SortedSet<T>` of `anti.collection.sorted`
now have every operation of "Maps" and "Sets" in
`docs/anti-language-additions.md`, including `range`, `floor`, `ceiling`,
`first`, `last`, `pop_first` and `pop_last`. `deserialize` is still missing,
since no collection has it yet.

## What was done

- The parser on main takes `union` as the name of a function, which resolves
  the blocker. The set gains `union(o)`. It walks both sets once in order and
  makes the new set from its own allocator. `tests/std/sorted_set.anti` checks
  it over small sets, an empty one, 500 elements, and a class element that
  owns memory.
- The map gains `==` through a generic `operator fn eq<K: Ordered, V: eq>` of
  the module, which calls `collection.equal`, as the entry of
  `docs/decisions.md` on `==` of a collection gives. The set's `==` moved from
  its class body to the same form. `tests/std/sorted_map.anti` compares maps
  that differ in a value, in length and in a key.
- `tests/errors/sorted.anti` holds the refusals: a lent walk of a set, a key
  with no `lt`, and `==` of a map whose values have no `eq`.
- `docs/decisions-sorted.md` records `union` and both operators.

## What failed and how it was fixed

- Before this change, `==` of two equal maps compiled and gave `false`: it
  fell back on the default `==` of a class value, which compares the fields.
  The new test showed it, and the module operator fixes it.
- The expected counts of teardowns in the owned part of the set test were
  wrong at first: `to_text` copies each element it writes, and each copy is
  torn down. A scratch program in `build/scratch/s3/` showed that `union`
  itself tears down nothing, and the expected output now counts the copies of
  `to_text`.
- `fmt_canonical` refused two edited doc comments,
  `build/drive/logs/s3-ctest-host.log`. `anti fmt` rewrapped them.
