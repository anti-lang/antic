# Failing functions: `may fail` and `fail`

The "Failing functions" section of `docs/anti-language-additions.md`. A
function is declared `-> R may fail` or `may fail`, `fail` leaves on the
error channel with an error or with a text, and the ABI stays the
hand-written convention. The standard library still writes that convention by hand,
which is a later step.

## What the compiler does now

- `may fail` is two contextual words after a signature, read where a
  result type ends. The lexer gained `fail` and `undo` as keywords.
- The checker gives a `may fail` function the ABI of the old convention.
  The result becomes `?*anti.error.Error`, and a declaration with a result
  gets one parameter of type `*R` after the ones it wrote. Every pass
  after the checker therefore sees the hand-written form, so the call
  forms, `catch`, `try`, the generated header and the library file needed
  no case of their own.
- `return v;` is checked against the declared result, writes through the
  out pointer and returns `none`. `return;` and the closing brace of a
  function without a result return `none`.
- `fail e;` returns the error. `fail "text";` calls
  `anti.error.Error.new(0, "text")`, which the statement keeps as a
  resolved symbol, the way `let m = p catch` keeps `NoneDereference.new`.
- `undo stmt;` is recorded as an exit action of its block and runs on the
  error exits alone, last declared first, before the `defer` statements
  and the teardowns of the same block. The error exits are a `fail`, a
  `try` that forwards, and a `return` of an `*Error` in a function that
  returns `?*Error`. The checker marks the statement and lowering reads
  one flag.
- A call to a `may fail` function needs a handler, and `try` outside such
  a function is refused. A `may fail` function with no `fail` and no `try`
  is a warning. The three messages are the ones the "Messages" section
  gives, which replaced two older spellings.
- The header writes `?*Error f(args, R *out)`, with the out parameter named
  `out`. It declares `struct anti_Error;` once when a signature names it,
  and puts one line above the prototype saying the function may fail.
- The library file records the flag, in a bit of the marks byte of a
  module item and of a function of a class body. `ANTL_VERSION` is 30.

## Tests

- `tests/programs/may_fail.anti`: both forms of `fail`, a scalar and an
  aggregate result through the out pointer, a function without a result,
  `try` forwarding, `fail e;` from inside a handler, a `try` block, and
  `undo` on the fail path and not on `return`, nested and in order.
- `tests/programs/may_fail_table.anti`: an abstract entry declared
  `may fail`, two replacements and a call through the pointer.
- `failing_modules_release` and `failing_modules_dev`: a library module
  whose functions are `may fail` and a program that imports it, so the
  flag and the ABI travel through the `.antl`.
- `clib_failing`: the header form, compared against `tests/dump/failing.h`
  and called from C on both paths.
- `listing_error_failing`, `listing_error_fail_forms`,
  `listing_error_fail_no_import` and `warning_never_fails`: the refusals
  and the warning.

## What failed and how it was fixed

- The first ASan build crashed in `run_defers`. `realloc` left the new
  `undo` field of an exit action unwritten, and the first pass read it.
  Every field is now written in one place, `push_exit_action`.
- An export function that may fail was refused, because `Error` is not an
  `export class`. `c_representable` now takes the class itself, since the
  header declares the tag and C never reads the layout.
- `raw_output` failed before this step, on a `git rev-parse` in
  `tests/run_release_dry_run.cmake` that captures output without
  `ENCODING NONE`. Its own commit fixes it.
- The docs-style checker reported findings in `src/ast.h`, `src/lexer.c`
  and `tests/unit/test_modules.c` that stand at `HEAD`. Runs of terse
  trailing field comments are joined into one sentence, so a full stop on
  one comment of a run splits it. Their own commit closes them.

## Provisional entries

`docs/decisions.md` gained a "Failing functions" section. Seven entries
carry `[provisional]`: the error exits that `undo` runs on, the order of
`undo` against `defer`, the refusal of `may fail` on `construct` and
`destruct`, the refusal on an `extern fn`, the name `out` of the out
parameter, an export signature naming `anti.error.Error`, and the line
the header writes above a prototype that may fail.

## Gates

Zero warnings from the compilers. 506 tests on the host, 505 under each
sanitizer preset, all passing. The logs are under `build/drive/logs/`:
`build.log`, `test.log`, `asan-test.log` and `ubsan-test.log`. The
docs-style checker reports nothing on the files this step touched.

The pinned clang prints `ld: warning: ignoring -lto_library` at every
