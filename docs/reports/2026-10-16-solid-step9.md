# Solid: step 9, `anti.trace` and guarded state

The step fixed the findings of step 9 of "Fix steps" in
`docs/audit/summary.md`: S314, M305, M318 and M361. It ran in one session
on 2026-10-16. The logs lie in `build/drive/logs/`, under names that start
with `step9-`.

## Findings closed

| Finding | Commit | Cause |
|---|---|---|
| S314 | `bd5e69c6`, `711ad686` | `Profiler`, `ErrorMonitor` and `ChangeJournal` wrote plain tables from every thread that reached a hook, and `Composite.add` took a slot with no guard. |
| M305 | `d62175c5` | `handlers_of` read no result of `Composite.add`, so the ninth handler of a `trace` key belonged to nothing. |
| M318, `SharedRandom` | `a7315143` | `SharedRandom` inherited the `reseed` of `Random`, which wrote the state with no lock. |
| M318, `FileConfig` | `58987147` | `read` deleted the old document while `has` and `text_of` of another thread read through the pointer they had loaded. |
| M318, `Logger` | `82850caa` | The class comment invited a program to write `name`, `level` and `format`, which every logging thread reads with no lock. |
| M361 | `5f15d339` | Three notes described handlers that counted atomically in all seven, a `start` over `anti_rt_conf_get`, a key of one name, and format version 57. |

`d1fdfaf9` writes the commits into the summary. `e628ca03` writes the
digests of `trace_handlers` in the manifest of `emit_identity`. The LLVM
text of that program changed with `anti.trace` on all six targets, by
`bd5e69c6` and `d62175c5`, and antic did not change.

- S314. Each of the four handlers holds a `Mutex` around its tables, in
  the hook that writes them and in every function that reads them.
  `Composite` writes the slot before it stores an atomic count.
  `std_trace_profile_threads` lost about 3000 of 320000 calls and once
  gave 60 names for 64 slots. `std_trace_errors_threads` ended 3 to 30 of
  4000 runs with parts of two failures, `std_trace_journal_threads` read
  thousands of torn names and `std_trace_composite_threads` lost a slot in
  14 to 17 of 2000 runs, `step9-tp.log` and the runs beside it. All four
  give their expected output now.
- M305. `install_deletes_a_handler_past_the_slots` of the `tests` block
  counted one object left alive, `step9-m305a.log`. The name past the
  eighth now writes one line and its handler is deleted.
- M318. `std_random_shared_reseed` drew numbers outside the sequence of
  the seed in 25 runs of 25. `std_config_threads` ended with a
  segmentation fault, and its form with one thread passed.
- The `Logger` part keeps its fields unguarded. See the provisional entry
  and the question below.

`last_message` of `ErrorMonitor` still gives a `str` into the monitor,
which the next failure writes over. Its comment and the note say that a
program reads it after the failing threads stopped, and calls `report`
while they run.

## Provisional entries

One entry of `docs/decisions.md`: the fields `name`, `level` and `format`
of `anti.log.Logger` stay plain public fields. A program writes them
before it starts the threads that log, and changes the logger of running
threads with `log.set`.

## Question

The entry on `anti.log` keeps `log.logger().level` as a field the program
writes. A guard needs a setter under a lock and fields a program cannot
write, which changes that entry and adds public items. Without one the
race stays in the program's hands, as the provisional entry has it.
Which does Eddie want?
