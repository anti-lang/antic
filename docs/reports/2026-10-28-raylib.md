# anti.raylib

The session of 2026-10-28 built `anti.raylib`, after Eddie lifted the freeze
for it under "Feature freeze of 2026-10-14" in `docs/decisions.md`.

## What changed

- `e030a9a5` drops the runs on the two VMs from the entry of 2026-10-28, as
  Eddie decided that day. A program links for every target from the Mac and
  runs on the Mac.
- `eec4c73c` fixes T208. On macOS `_NSGetExecutablePath` gives the path of
  the program as the command line spelled it, so `anti` run as `../anti`
  took the first clang on `PATH` in place of the pinned clang of the tree.
  `self_path` resolves the path with `realpath`. The case
  `anti_bind_clang_of_the_tree_relative` holds it.
- `202876cc` builds `anti.raylib`. `src/native/raylib.cmake` runs
  `anti bind --clang` on `raylib.h` of the pinned raylib with the pinned
  clang alone on `PATH`, and compiles the module into
  `std/anti/raylib.antl` of the runtime archive. The tree holds no file of
  it. A program whose import closure holds the module links `libraylib`,
  then `libminiaudio`, and the system libraries of its target with no
  option, as a program of `anti.regex` links PCRE2. antic reads the
  `link framework` and `link linux` lines from the library file. Linux
  links in the glibc mode, and Windows takes the import libraries of
  gdi32, user32, shell32 and winmm from the sysroot. A program below the
  default level is refused with the level of each library. A library for C
  names the same libraries on the line it prints.
  `tools/check-offline.cmake` imports `anti.raylib` and passes no option.

`raylib.h` holds no inline function, so `anti bind` writes no shim for it.
The binding is the same text for all six targets, so the build binds it
for the host alone.

## The acceptance check

A copy of `pythagoras-tree` in `build/scratch-raylib/pythagoras`, with
`src/tree/raylib.anti` deleted and `import tree.raylib as rl;` changed to
`import anti.raylib as rl;`, built from that directory:

```sh
A=../../host
mkdir -p build/lib/tree
for m in tuning geometry; do
	$A/antic -c --runtime $A/runtime -I src -I build/lib \
		-o build/lib/tree/$m.antl src/tree/$m.anti
done
$A/anti test --work build/test-work -I src -I build/lib --runtime $A/runtime \
	src/tree/geometry.anti
$A/antic --runtime $A/runtime -I build/lib -o build/tree src/tree/main.anti
```

The 18 tests of `tree.geometry` pass, and `build/tree` links with no
framework option and no `libraylib.a` on the command line. It loads Cocoa,
CoreVideo, IOKit and OpenGL.

## The observation on `--runtime`

`build/host/anti bind --clang` without `--runtime` refuses with "the
runtime archive holds no sysroot for macos-arm64". That is no defect. By
the rule of `user_runtime_archive` the archive stands above the directory
of the program or in the user's data directory. A tree keeps it in
`build/host/runtime`, below the program, so neither place holds one, and
`antic` of the tree asks for `--runtime` the same way. The test
`anti_bind_message_clang_no_runtime` holds the message.

   `rt` to the table of "The system libraries of raylib and miniaudio". A
   program then needs `libGL.so.1` at start. Keep that, or link the four
   libraries of the table?
2. `anti.raylib` stands in the package `anti` under 0BSD. The notice of a

   it name raylib?
3. `docs/tooling.md` says `import anti.raylib;` works with an empty
   `anti.toml`. `anti build` refuses a manifest without `[package]` and
   `name`, so the test takes a manifest of `[package]` alone. Is that what
   the sentence means?
4. raymath, rlgl and rcamera are no part of `anti.raylib`, which the
   decisions bind from `raylib.h`. `libraylib.a` exports the functions of
   raymath, since `rcore.c` defines `RAYMATH_IMPLEMENTATION`. Should a
   module bind them?
5. The refusal of `anti bind --clang` without an archive says the archive
   holds no sysroot. Should it say that no archive was found?
