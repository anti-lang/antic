# The anti.9 pin and the fix of T211

The branch `t211-trial` came onto `main`, rebased on `8cfe0af1`. The two
macOS hosts take `23.1.1-anti.9` of `anti-lang/llvm-tools` with its three
new tools. The symbols archive of a macOS program resolves frames without
the build directory, and the program is the same bytes in any directory.
Eddie's answers stand as "Answers of 2026-11-07, sixth set" in
`docs/decisions.md`.

## What changed

- `055694bc` and `a469ba64` are the two commits of the trial, rebased. The
  row of T211 names `055694bc` now.
- `b41f4cda` records the sixth set. Q1 puts the DWARF of the dSYM in the
  archive, and Q2 keeps a macOS program independent of its directory. By
  Q3 a host whose package lacks `llvm-strip` or `dsymutil` refuses a
  release build, with no fallback.
- `15a5d49d` pins a tag per host. `tools/llvm-pin` and `tools/clang-pin`
  hold `<host>-tag` and `<host>-digest` for each host. The macOS hosts take
  anti.9 with the digests of its `SHA256SUMS`, whose signature checks
  against `tools/keys/release.pem`. The Linux and Windows hosts keep anti.8
  and their digests. `antic_release_pin` of `tools/pins.cmake` is the one
  reader, and `release_pins` refuses a row of a host read or spelled
  anywhere else. `antic_llvm_host_tools` of `tools/pinned-tools.cmake` adds
  `llvm-objcopy`, `llvm-strip` and `dsymutil` for a tag that counts 9 or
  more. `bin/` of the runtime archive and the package of such a host carry
  them. The entry of the format stands under "Scope and toolchain".
- `f2c8d50f` builds Q1 and Q2. The archive of a stripped macOS program
  carries `<stem>.dwarf`. The map and `anti symbols resolve` read the
  lines from it, through the symbol and the start that the debug map of
  the twin names. The link names its LTO object relative to the absolute
  build directory with `-oso_prefix`, and `dsymutil` takes
  `--oso-prepend-path`. Only a program that `anti build` strips gets the
  prefix, so `antic -g` and `--memory-checks` keep the absolute path.

## The readers of the pins

- `tools/fetch-release.cmake`, `tools/clang-release.cmake` with its two
  callers, `run_no_tool_packed.cmake` and `run_release_pins.cmake` go
  through `antic_release_pin`. `antic_clang_release` takes the host now.
- `tools/pack-anti.cmake` refuses a tools directory of a host that lacks a
  tool of its tag. `tools/release.sh` runs `tools/get-llvm.cmake` for every
  host, which downloads nothing when the digest of the pin is installed.
  It skipped a host whose `llvm-version` stood, which would have kept a
  directory of anti.8 for macos-x86_64.
- `tools/upstream-sources.cmake` reads neither pin, and its record names
  no LLVM component, so nothing changed there.

## Tests

- New: `symbols_moved_frame_without_build` removes the build directory
  before it resolves, and `symbols_same_bytes_macos-arm64` and
  `symbols_same_bytes_macos-x86_64` build in two directories. Both failed
  first: the frame resolved to `moved.anti:18`, and the programs differed
  in 40 bytes.
- `own_tools` refuses a release build whose archive lacks `llvm-strip` or
  `dsymutil` by its path, with the tool on the search path, and finds no
  program in `dist/`. `pinned_tools` checks the three on a macOS host, and
  `unit_link` checks `-oso_prefix`.
- On the Mac `fault_archive_map_unread` takes open 48, and
  `fault_dsym_unread_for_map` and `fault_archive_dsym_unread` replace
  `fault_debug_object_unread`.
- `link_identity_macos-arm64` showed that a new function in
  `src/rt/symbols.c` changes every macOS program. The lookup reuses
  `anti_rt_macho_object_line` on the dSYM, and the runtime stays as it was.
- The host suite ran in three parts before each code commit, and every
  test passed. It took 394 s, 274 s and 338 s for the pin, and 389 s,
  273 s and 338 s for the dSYM. Both sanitizer suites ran in six parts
  before the push, 6964 tests each, and every test passed. `asan` took
  289 s, 229 s, 262 s, 194 s, 446 s and 447 s. `ubsan` took 272 s, 196 s,
  261 s, 206 s, 468 s and 465 s.

## The Linux and Windows hosts until anti.10

The VMs are down, so no suite of either host ran, and the fault counts
of `tests/anti-build/messages.cmake` stand unmeasured there. Every count
of this step and of the trial was measured on the Mac. By the code, a
release build of a program for a Linux or a macOS target stops at the
missing `llvm-strip`, by Q3. A Windows target strips nothing, and
`anti test --release` strips nothing. These tests fail by that reading:

- Both hosts: `symbols_same_code_` of the four Linux and macOS targets,
  `symbols_layout_linux-x86_64` and `_linux-arm64`, both
  `symbols_same_bytes_` tests, `symbols_resolve_elf`, `linux_modes`,
  `anti_option_symbols_target` and `own_tools`. `own_tools` expects the
  name of `dsymutil`, and the build names the missing `llvm-strip` first.
- Linux alone, where the host target is ELF: `anti_build`,
  `anti_internal`, `anti_symbols`, `symbols_moved_frame`,
  `anti_build_raylib`, `anti_build_no_package_program`, `_named`,
  `_version` and `_license`, `anti_option_release_path`,
  `anti_option_symbols_from`, and `anti_reuse_build_release_` of
  `unchanged`, `source`, `import`, `option`, `compiler`, `native`,
  `same_size` and `unreadable`.
- Linux alone, the fault cases whose fault lies after the strip:
  `fault_map_not_written`, `fault_symbols_not_written`,
  `fault_program_unread_for_id`, `fault_debug_program_unread`,
  `fault_archive_entry_unread` and `fault_archive_map_unread`.

## Notes

- The tools archive of anti.9 holds `llvm-strip` as a second file of the
  bytes of `llvm-objcopy`, not as a link.
- `dsymutil` exits with 0 when it cannot open an object of the debug map,
  and writes a dSYM without lines. The first build of Q2 did that, and
  `symbols_moved_frame` caught it.
