# Solid: step 20, runtime readers under a sanitizer

The step fixed the two findings of step 20 of "Fix steps" in
`docs/audit/summary.md`: M314 and M315. It took no decision of
"Decisions of 2026-10-11", since none names either. No later step names
either finding. It ran in one session on 2026-10-17. The logs lie in
`build/drive/logs/`, under names that start with `s20-`.

## Findings closed

| Finding | Commit | Cause and remedy |
|---|---|---|
| M314 | `b1a3820e` | Every prefix of a Mach-O file went through the Mach-O readers, and no ELF file was ever cut short. `test_symbols.c` now cuts an ELF file at every byte, each copy in memory of its own. It puts `e_shoff` and `e_shstrndx` outside the file and gives more section headers than the file holds. It gives a symbol table whose size is no multiple of a symbol or runs past the file, and a link to a string table that is no section. It reads a line table of DWARF 2 and one of DWARF 3, then each cut short at every byte. |
| M315 | `f6e270fc` | The malformed input of `Object.deserialize` ran only inside an Anti program, which links no sanitizer, and no C test program compiled `registry.c`. The new test `rt_deserialize` compiles `registry.c`, `object.c` and `json.c` with stand-ins for the classes, the registry and the loader, as `test_conf_race.c` does. Each input is a heap copy without a NUL. A counting allocator checks that a refused text gives back every block and tears down every object it prepared. |

- M314: the checks of the readers were present at the audit, and the
  gap was the test. A mutation that removes the bounds check of the
  section headers makes the new cases a `heap-buffer-overflow` under
  ASan, `s20-mut-run.log`.
- M315: the cases of `tests/std/deserialize_input.anti` come back. Next
  to them stand tuples, arrays of one and two levels, owned objects,
  slices and values, a name that two modules declare, the depth limit,
  and every prefix of five whole texts. A mutation that lets the reader
  see one byte past its text is a `heap-buffer-overflow`,
  `s20-mut2-run.log`. One that keeps one block back fails the count,
  `s20-mut3-run.log`. The sources were restored before the commits.
- M315 also said that the description of the preset `asan` claimed its
  runtime ran under the sanitizer. `f6e270fc` names what does.
- M315 counted 23 runtime files that run under no sanitizer. Step 20
  names `registry.c` and `object.c`, and `object.c` stood in two C test
  programs already. The other files that run only inside Anti
  programs, `trace.c`, `threads.c`, `lock.c` and `patterns.c` among
  them, have no C test program yet. No step of the summary names them.
- `b1a3820e` and `f6e270fc` change no file of `src/`. `10fd33f1`
  records the commits in the audit.

## New finding

- T143, fixed `ca450252`. Under UBSan, `rt_deserialize` stopped at a
  call to `anti_lang_Object_serialize` through the function type
  `void (*)(const void *, void *)`. `serialize_object` of `object.c`
  called every serialize entry through it. C11 leaves a call through an
  incompatible function type undefined. The runtime of an Anti program
  carries no sanitizer, so nothing saw it before. The new test shows it,
  so the fix belongs here. The test stopped in the ubsan tree before the
  fix and passes after it. The run after the fix wrote
  `s20-ubsan-des.log` again.
- The test first assumed that `😀` reads as one character.
  The DESIGN of `json.c` refuses every `\u` escape of a surrogate half,
  so the test keeps that behaviour.
