# R10 closed: Object.deserialize and interpolation take an Allocator

`Object.deserialize(input, from)` takes the object, every string and every owned object it makes from the `anti.mem.Allocator` `from`. The caller gives them all back through `from`. The form without an allocator is gone, and the R10 entry of `docs/decisions.md` gives way to the rule it deferred. `f"..."(from)` and `rf"..."(from)` take their text from `from`, and `f"..."` keeps the C library.

## Commits

1. `5297b80`. `rt/registry.c` takes every block of a read from the allocator: the object at an alignment of 16, a buffer of elements at 16 and a string at 1 with its NUL. The runtime calls `alloc` and `free` as table entries 8 and 9. A text that fails gives each block back, the last first. The checker types the parameter as `*anti.mem.Allocator` and refuses a module without that import. Tests: `std_deserialize_alloc`, which counts every block through a remembering allocator, an interface sub-object and an `ArenaAllocator`. `listing_error_deserialize_alloc` and `listing_error_deserialize_no_import` hold the refusals. The five tests that read objects back now read into an `ArenaAllocator`. The dev test links the object of `anti.mem`.
2. `8cdc942`. The parser keeps an argument list right after a literal on the literal. The checker ends the calls with `Builder.take_in(from)` in place of `take()`. `take_in` copies the bytes and their NUL into memory of `from` and frees the builder's buffer. `anti.text` imports `anti.mem`, so `mem` builds second. Tests: `std_format_alloc`, `listing_error_format_alloc`.
3. `b1735fc`. `CLAUDE.md` records both forms and the counts.

## What failed and how it was fixed

- `program_deserialize_dev` did not link, because a dev link takes an imported module only as an object on the command line. The fixture `dev_object_mem` compiles `mem.antl` for it. `shared_class_dev` failed the same way once `anti.text` imported `anti.mem`, and its list of modules gained `mem`.
- `link_identity_macos-arm64` failed after the change to `rt/registry.c`. The notice of the program holds the build id of the runtime. A build of `f863f7a` passed, and the two executables differ in that id, the UUID and the signature alone. The Mac's digest was written.
- `emit_identity` changed for `deserialize` at the first commit. It changed for `format_strings`, `object_model`, `switch_str` and `transient` at the second, since `take_in` joins the table of `Builder`. The manifest was written with `WRITE=yes`.
- Two mistakes in the new tests: a quote inside `{...}`, which needs `f#"..."#`, and a private field set by a literal.
- The docs-style checker reads `CMakeLists.txt` as Markdown. It finds 35 findings in the root file, as before, and 176 in `tests/CMakeLists.txt`, against 175 before. The new one is the `add_test` code after the added comment, read as a sentence. The added comment lines were read by hand against the rules. Every other touched file reports nothing.
- The host link prints `ignoring -lto_library` three times, at `f863f7a` as well (`build/drive/logs/build-head.log`).

## Provisional entries added

Under "Object model": the allocator is the second argument `from`, and the object itself comes from it at 16. No `destruct` runs on such an object. A failed text gives every block back. A module that calls `Object.deserialize` imports `anti.mem`. Under "Interpolation": the allocator stands in an argument list right after the literal. The literal ends with `take_in(from)`, which copies at the end.

## Questions for Eddie

- The syntax `f"..."(from)` is the gap procedure's choice, since no document names one. Is it the form you want, or a word such as `f"..." in from`?
- `take_in` is `pub`, so it stands in the table of `Builder` and every program that uses the class carries it: 174 lines of assembly for `switch_str` on macos-arm64. Should the form call a function outside the class instead?
- A `construct` without arguments still runs on a read object, and memory it takes is not given back through `from`. Should `Object.deserialize` with an allocator skip it?
