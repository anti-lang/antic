## Decision 16, left

`4d7515f7` built decision 16: Ninja 1.12.1 for windows-arm64 in
`tools/ninja-pin`, `tools/get-ninja.cmake` to install it under
`anti-vm`, and a script of step 5 that put it on the path and loaded no
`vcvarsall.bat`. On the VM a fresh configure without `vcvarsall.bat`
stopped, `s24-win-build.log`:

```text
CMake Error at .../Modules/Platform/Windows-Clang.cmake:149 (enable_language):
  No CMAKE_RC_COMPILER could be found.
```

CMake turns the language RC on for clang on Windows without a condition.
Under `vcvarsall.bat` the cache names
`C:/Program Files (x86)/Windows Kits/10/bin/10.0.26100.0/arm64/rc.exe`,
`s24-win-rcprobe.log`. The call therefore loads the Build Tools for
Ninja and for the resource compiler of the Windows SDK, a tool of the
host, and the pinned release of `anti-lang/llvm-tools` holds no
`llvm-rc`. `5bf0cb11` takes `4d7515f7` back whole, and the summary says
the call waits for decision 16. The Ninja the session installed under
`%LOCALAPPDATA%\anti-vm\ninja` on the VM is removed.

The question for Eddie: where does the configure on Windows take its
resource compiler? Three answers stand open. One is `llvm-rc` in a new
release of `anti-lang/llvm-tools`, named as `CMAKE_RC_COMPILER` by the
configure. Another keeps `vcvarsall.bat`, or the `bin` directory of the
Windows SDK on the path, and amends decision 16. The third is another
way to answer CMake. No target of the build compiles a `.rc` file.
