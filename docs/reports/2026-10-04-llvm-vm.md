# Step vm of the LLVM back end, blocked

Step `vm` of `docs/work-order-llvm-back-end.md`. Both VMs ran the export of
`3eaa2018`, which is `origin/main`, built with the pinned toolchain of
`23.1.1-anti.5` and configured with `-DANTIC_BACKEND=llvm`. The configure of
anti-windows installed `opt` and `llc`, which its toolchain lacked. The step is
BLOCKED on one question, at the end. Nothing is fixed, committed apart from this
report, or pushed. The runs under `--backend native` did not take place, since
they follow the fixes.

## Causes

- A. `llvm_datalayout_pin`. clang finds the GCC 13 of the VM for
  `aarch64-unknown-linux-gnu` and adds `+outline-atomics` at `armv8.0`. The Mac
  has no GCC, so the answer depends on the host. With `--sysroot` of the pinned
  sysroot, or `--gcc-toolchain` of a missing directory, clang on the VM writes the
  string of antic. The fix is in the test.
- B. Eight Linux tests: `std_backtrace`, `anti_symbols`, `trace_stack`,
  `trace_stack_dev`, `trace_forged` and the three `trace_copies*`. The text gives
  every function `"frame-pointer"="none"` outside macOS arm64, as "Attributes and
  metadata" says, and no `uwtable` on ELF. The walk of `anti_rt_trace_walk` follows
  frame records, so it reads no chain. A trace ends at the first frame or reads a
  stray record and crashes. `stack_trace.linux-arm64.ll` holds the text. With
  `"non-leaf"` on every target but Windows, in the scratch tree of the VM alone,
  the eight pass (`linux-fp-experiment.log`).
- C. `debug_info` on Linux. The compile unit is `LineTablesOnly`, and the DWARF
  of the Linux program holds the unit of `app.anti` with no subprogram in it, so
  gdb names the frame by its symbol, `app.twice$3cint$3e`. lldb on the Mac reads a
  subprogram from the same text. The likely fix, not yet tried, is
  `debugInfoForProfiling: true` on the unit, or `FullDebug` with the same nodes,
  to keep one subprogram per function as "Debug information" asks.
- D. `trace_stack_g` on both. `stack_trace.g.llvm.pattern` and
  `stack_trace.llvm.pattern` expect the C frame below `main` without a line. musl
  under `-g` names `__libc_start_main.c:95`, and the CRT of Windows
  `exe_common.inl:288`. The fix is in the patterns.
- E. `anti_build`, `trace_stack` and `trace_stack_dev` on Windows. A COFF text
  writes a subprogram per function in every build, with `line` and `scopeLine` of
  the declaration (`stack_trace.windows-arm64.ll`). CodeView turns that into a
  line record, so a build without `-g` carries lines. The fix is line 0 on the
  subprogram outside `-g`, as the entry on `-g` of the LLVM back end says.
- F. `trace_stack_g` on Windows names `main` at line 38, the call, where Eddie's
  entry on inlined frames asks for line 14 of the inlined callee. DbgHelp's
  `SymGetLineFromAddr64` reads the line of the outer function. The fix is in
  `src/rt/platform_windows.c`, through the inline context of DbgHelp.

## The question

B needs a decision the documents do not give. "Attributes and metadata" in
`docs/work-order-llvm-back-end.md` sets `"frame-pointer"="none"` on Linux and
Windows: "Linux and Windows do not require it". Three entries need the frame
records on Linux. `docs/notes/traces.md` says the walk follows the records "which
antic keeps in every function that calls another". The entry on the unwinder of
`--memory-checks` in `docs/decisions.md` has the report walk "the Anti frames by
their frame pointers". "Memory checks" of the work order says every function also
gets `.eh_frame` under LLVM, which no `uwtable` on ELF gives. The options:

1. `"frame-pointer"="non-leaf"` on Linux and macOS x86_64 as on macOS arm64,
   what the native back end keeps. It costs one register in a function that
   calls another. The experiment above passes with it.
2. `"none"` stays, ELF takes `uwtable(sync)`, and the walk on Linux reads
   `.eh_frame` through an unwinder. A musl program then links one, which the
   runtime archive holds for the glibc targets alone.

macOS x86_64 has the same `"none"`. No test runs a trace there, so it is not
checked.

## Decision

Eddie decided on 2026-10-04 for option 1. Every function keeps its frame record on every target but Windows. The attribute is `"frame-pointer"="non-leaf"` on Linux and on both macOS targets, and `"none"` on Windows. The entry stands in `docs/decisions.md` after the entry on inlined frames. "Attributes and metadata" of the work order says the same. The redo of this step applies it and fixes causes A, C, D, E and F as this report describes. It then runs both VMs under both back ends.
