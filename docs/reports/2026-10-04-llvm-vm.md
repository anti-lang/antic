## What failed and how it was fixed

The first run found six causes, A to F, listed under "The first run" below.

- B, eight Linux traces. `be97fac9` writes `"frame-pointer"="non-leaf"` on every target
  but Windows, as Eddie decided. `unit_llvm_emit` checks the attribute on both Linux
  targets and on macOS x86_64.
- A, `llvm_datalayout_pin`. `ac7aa57f` gives clang `--gcc-toolchain` of a missing
  directory for a Linux triple, so the GCC of anti-linux adds no `+outline-atomics`.
- D, `trace_stack_g`. `a54ddae0` lets the C frame below `main` carry any line in the
  two LLVM patterns.
- C, `debug_info` on Linux. `f2148df4` makes the compile unit `FullDebug`. Under
  `LineTablesOnly` llc wrote no subprogram for a function that inlines nothing. A probe
  on anti-linux showed gdb then names `app.twice<int>` (`dbg/vm-probe.log`).
- E, `anti_build`, `trace_stack` and `trace_stack_dev` on Windows. `db75ff66` gives a
  COFF subprogram line 0 without `-g`. The VM run at `f62091a7` still failed the three:
  LLVM writes the record of a function only with a location, so each function keeps a
  line table of line 0, and DbgHelp named `stack_trace.anti:0`. `fd2bc8b6` reads line 0
  as no position on Windows. `anti_build` counts the CodeView entries of a line other
  than 0: none in release, some in dev. The rerun of the part overwrote the log of the
  failing run, which read `stack_trace.inner stack_trace.anti:0` for `trace_stack_dev`
  and "the release build passed -g" for `anti_build`.
- F, `trace_stack_g` on Windows. `f62091a7` reads the line through the inline context
  of DbgHelp, `SymGetLineFromInlineContext`, so the frame of `main` names line 14 of the
  inlined callee.

The `.ll` texts of the first run stand in `build/drive/logs/vm/stack_trace.linux-arm64.ll`
and `stack_trace.windows-arm64.ll`.

## Provisional entries added

## The first run

The first run at `3eaa2018`, reported in `aa4255f3`, failed 11 tests in each Linux
suite under the LLVM back end and 4 on Windows. Its logs lie in `build/drive/logs/vm/`.
Its causes:

- A. clang on anti-linux finds GCC 13 and adds `+outline-atomics` at `armv8.0`.
- B. `"frame-pointer"="none"` on Linux left the walk of a trace no chain of records.
- C. gdb on Linux named a frame by its symbol, since the DWARF held no subprogram.
- D. musl under `-g` names `__libc_start_main.c:95` and the CRT of Windows
  `exe_common.inl:288` in the frame below `main`.
- E. A COFF subprogram carried the line of its declaration without `-g`.
- F. DbgHelp read the line of the caller for an address inside inlined code.

The first report asked about B with two options. Option 1 keeps the frame record as the
native back end does. Option 2 keeps `"none"` and walks `.eh_frame` with an unwinder.
Eddie's decision, as it stood in the first report:

Eddie decided on 2026-10-04 for option 1. Every function keeps its frame record on every target but Windows. The attribute is `"frame-pointer"="non-leaf"` on Linux and on both macOS targets, and `"none"` on Windows. The entry stands in `docs/decisions.md` after the entry on inlined frames. "Attributes and metadata" of the work order says the same. The redo of this step applies it and fixes causes A, C, D, E and F as this report describes. It then runs both VMs under both back ends.
