# Trial of the fix of T211 by route (a)

Eddie approved a trial of route (a) of Q1 of "Answers of 2026-11-07,
fourth set" on the Mac, before the release of the new LLVM tools. The
trial stands on the branch `t211-trial` alone. The branch waits for the
published release of `anti-lang/llvm-tools` with `llvm-objcopy`,
`llvm-strip` and `dsymutil`, and it reaches neither `main` nor `origin`
before that release.

## What changed

- `4fd33413` builds route (a) with its tests.
- The commit after it adds this report and the hash of the fix to the
  row of T211.

A release build of `anti build --release` runs one call of antic, which
links with `-g`. `build_release` of `src/anti/build.c` copies the link to
`<stem>.debug` in the build directory, the twin of the symbols archive.
`driver_strip_debug` of `src/antic/driver_link.c` then writes the program
from the twin:

- ELF: `llvm-strip --strip-debug`, which keeps the symbol table.
- Mach-O: `dsymutil` writes `<stem>.debug.dSYM` from the LTO object that
  the debug map names, then `llvm-strip -S` drops the debug map.
- COFF: nothing runs. The PDB holds the debug information, so the
  executable of the link is the program, and its twin is a copy of it.

`build_symbols` links nothing now. It writes the map from the twin and the
archive from the twin, the map and, on Windows, the PDB of the one link.
The format of the archive does not change.

## The tools of the trial

The three tools came from a local build of LLVM 23.1.1, the recipe of the
pinned tools, in the scratch directory of the session. They went into
`build/host/runtime/bin`, the runtime archive of the host tree, where
`driver_archive_tool` finds every tool: `llvm-objcopy`, `dsymutil` and
the link `llvm-strip` to `llvm-objcopy`. `tools/copy-llvm.cmake` fills
that directory from `build/deps/llvm/bin` and removes no other file, so
`build/deps/` stayed untouched. Its listing and the SHA-256 of
`build/deps/llvm/bin` matched before and after. The three files left
`build/host/runtime/bin` at the end, and its digests matched the ones
taken before.

## Evidence

- `symbols_moved_frame` passes. The frame of the capture resolves to
  `com.example.moved.stop moved.anti:20` at 0x222b8, where it resolved to
  `anti.io.exit io.anti:36` before. Its line left
  `tests/known-failures.txt`, and the row of T211 says `fixed`.
- The new tests `symbols_same_code_<target>` build
  `tests/anti-symbols/moved` with `anti build --release` for each target.
  Each compares every section with an address of the program in `dist/`
  with the twin of the archive: the name, the size, the address and every
  byte of `llvm-objdump -s`. All six pass. Before the change five failed,
  and linux-x86_64 passed, as the report of T211 found.
- macos-arm64 and macos-x86_64: 15 sections each, identical. The program
  of macos-x86_64, built with `--cpu v1`, ran under Rosetta, and `anti
  symbols resolve` named `com.example.moved.main moved.anti:30` and
  `main` for its two frames. At `v1` opt inlines `stop` into `main`. The
  program of macos-arm64 keeps a valid ad hoc signature after
  `llvm-strip`.
- linux-arm64 and linux-x86_64: every section with an address is
  identical. The program is 78 KB to 80 KB below its twin, the DWARF.
- windows-arm64 and windows-x86_64: the program is the link, so the twin
  is the same file. No tool runs.
- Time of `anti build --release` of `moved` for macos-arm64 from an empty
  build directory, the Debug `anti`, 11 runs each. Before, with the two
  links: median 1.804 s, from 1.796 s to 1.830 s. After, with one link,
  `dsymutil` and `llvm-strip`: median 0.994 s, and 1.001 s in a second
  set of 11 runs. An LLVM build of another session ran on the Mac the
  whole time, so the figures stand under load.
- A program of `--memory-checks` keeps its lines for its reports, by the
  rule of `base_options` in `src/anti/build.c`. The first run of the suite
  showed it: `anti_memory_checks` lost the line `demo.anti:29`. The
  program of such a build is now the link as it stands, unstripped.

One property changed on macOS. The Mach-O UUID of the program depends on
the build directory now. ld64.lld computes it over the link, whose debug
map names the LTO object by its absolute path, and `llvm-strip` keeps
the UUID. Two builds of `moved` in two directories differ in 39 bytes:
the 16 of the UUID and the hashes of the signature over that page. Two
builds in one directory are identical, and the programs of the old path
were identical across directories. The build id of the notice does not
change, and neither do the code and the data. linux-arm64 stays
identical across directories. Windows was not compared.

## Tests

- The targeted groups ran before the full suite: the tests of symbols,
  `anti build`, the reuse of builds, the packages, `emit_identity`,
  `link_identity`, `pinned_tools`, `own_tools`, `pdb_guid` and the guards.
  Eight fault cases of `tests/anti-build/messages.cmake` failed, since the
  release build opens and writes other files now. Their counts were
  measured again on the Mac. `fault_debug_text_not_created` names
  `app.ll`, the one text of the link, and `fault_archive_entry_unread` now
  takes the open of the twin by `zip.c`, where it took the one of
  `symmap.c`. Three cases are new: `fault_debug_twin_not_copied`, and
  `fault_dsymutil_not_run` and `fault_strip_not_run` on macOS.
- The full host suite ran in three parts with `-j14`, 6962 tests. The
  first run, 410 s, 298 s and 344 s, failed `anti_memory_checks`, above.
  After the fix the suite ran again, 394 s, 293 s and 349 s, and every
  test passed. The two `mimalloc_environment` tests skipped.
- No test failed because the tools are not pinned, since the trial put
  them into `bin/` of the runtime archive of the host tree. Without them
  a release build for Linux or macOS stops with `antic:
  <runtime>/bin/llvm-strip is missing. The package holds it in bin/ beside
  antic.` and exit status 1, which a run after the restore showed.
- No sanitizer suite ran, since nothing is pushed. The VMs stayed down.

## Questions for Eddie

1. The dSYM: `dsymutil` writes `<stem>.debug.dSYM` beside the twin, and
   nothing reads it yet. The archive holds the twin and the map, and
   `anti symbols resolve` reads the line tables from the LTO object that
   the debug map names, on the machine that built it. Should the archive
   carry the DWARF file of the dSYM, read by `resolve` where the object
   is gone? Or should the build skip `dsymutil` until it does?
2. The UUID: should the Mach-O program stay independent of the build
   directory? `-oso_prefix` of ld64.lld would write the path of the LTO
   object relative to a directory. `resolve` and `dsymutil` would then
   need that directory to find the object.
