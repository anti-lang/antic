# The findings of the test run

The test run builds the suite out until it holds every construct of the
language in every place it can stand. It holds every diagnostic and every
option as well, and it changes no code under `src/`. A defect that a test
shows gets the next free id and one row in the table below. Its test stays
in the suite, written as the rule says the program must behave. One line of
`tests/known-failures.txt` names the test and the id, so the suite expects
that test to fail. Decision 30 of "Decisions of 2026-10-11" in
`docs/decisions.md` states this.

A row holds seven cells:

- The id. The first is `T001`, and each new finding takes the next number.
- The test that shows the defect. A second test that shows the same defect
  names the same id in `tests/known-failures.txt` and gets no row.
- The construct and the context it stands in.
- What happens.
- What the rule says and where it says it.
- The grade.
- The state: `open`, `fixed` followed by the commit of the fix, or `no
  defect`. A row is `no defect` where a decision of Eddie's replaced the rule
  its test held, and the commit that changed the test follows.

The three grades:

- `severe`: a wrong result at run time, a memory error or a crash of a
  program antic built.
- `major`: a crash of antic or anti, or a rule the checker does not hold.
- `minor`: the text or the position of a message.

A finding that two grades describe takes the higher one. A program that
compiles where a rule refuses it is `major`. It is `severe` when the
program then gives a wrong result or a memory error that no rule of the
run time covers. The review of 2026-10-13 graded T017, T020, T044, T053
and T093 again by this reading.

Eddie answered the four questions of that review on 2026-10-13. "The
review of the test run" under "Rules of 2026-10-13" in `docs/decisions.md`
holds the answers as Q1 to Q4:

- Q1. The sentence on two grades stands, and so do the five grades the
  review changed.
- Q2. T019, T028 and T106 stay three rows. They hold one missing refusal
  and two kinds of crash, and each has its own fix.
- Q3. T043 is `severe` by that sentence. The origin is a value of the
  program, so a wrong one is a wrong result at run time.
- Q4. `CLAUDE.md` decides when the sanitizer suites run: before a push with
  any change outside the documents. A step that adds a test or closes a
  finding runs both.

A `|` inside a cell is written `\|`. The fix of a finding removes its lines
from `tests/known-failures.txt` and writes `fixed` into the state of its
row. The row stays.

A defect that shows on some hosts alone names them in its row. The line of
its test ends with `host=` and their systems, `macos`, `linux` or
`windows`, with a `,` between two. The suite of such a host expects the
test to fail, and that of every other host expects it to pass.

The test `known_failures` reads this table and the list. It fails when:

- a line of the list names no test
- the `host=` of a line names a system that is none of the three, or one
  twice
- the id of a line has no row, or a row marked `fixed`
- an open row has no line
- a row does not end with a grade and a state
