# Nested types

Choices made for nested types in each pass. They describe the inside of the
compiler. `docs/decisions.md` holds what a reader of the language or a user of
the tools can observe, under "Nested types".

- The parser reads a nested type in the loop of the fields of a class body and in the loop of its functions. It may therefore stand anywhere among them. `starts_nested` looks past the words that may stand before a type, `pub`, `abstract`, `final` and the others, to `struct`, `union`, `enum`, `class` or `variant`. It runs before `starts_member`, which would take `abstract class` for a function.
- `nested_type` reads the declaration with `item`, the reader of a module item, so a nested type takes every form a module-level one does. A visibility word, a union and a variant are each reported. The declaration is read whole, so the rest of the body reports its own errors.
- A class item holds its nested types in `nested`. `push_item` adds each one to the items of the module, before the class that declares it, under the full name. The name as written stays in `local_name`, and `outer` points at the class. The nested types come first, so the checker has declared their fields when a default of the class names one.
- The checker keeps the item whose body it checks in `within`. `sema_module_find` looks a name up in the nested types of `within` and of each class around it, then in the module scope, and `sema_lookup` does so when it reaches the module scope. Each pass that resolves a name of an item sets `within`: the bases, the enum values, the fields, the members, the defaults of the parameters, the bodies and the constants. `sema_within` gives the class of a member and the item itself otherwise.
- `refuse_nested_in_signatures` runs in `check_types` for a class with nested types. The members have their types by then. It compares each type a signature reaches with the types of the class's own `nested` list, since a type nested deeper has no name in its body. A `pub` constant is resolved quietly there, because a constant of a body is evaluated only where it is named.
- The export check takes the class whose nested types cross with it. `c_representable` accepts a type nested in it at any depth, and `check_nested_fields` checks the fields of each nested type the layout reaches.
- The header finds the nested types of an export class from the types alone, by the module and the prefix of the full name, so the header written from a library file equals the one of `--lib`. `collect_nested` walks the fields through pointers and arrays and puts each type after the ones it reaches. `nested_views` writes the typedefs, then each layout, with `struct_fields` and `class_fields`, the loops that `aggregate` and `class_view` use as well.
- The library file carries a nested type under its full name when a field of a public item reaches it. It carries it as any type of the table. Its symbol is private, so no other module finds it by name, and the format keeps version 54.
